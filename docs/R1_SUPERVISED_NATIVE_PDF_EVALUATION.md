# r1 합성 PDF 추출 기능: 평가 결과와 사용 범위

## 한눈에 보는 결론

이 기능은 현재 프로젝트에서 만든 B/L, Invoice, Packing List PDF에서 필요한 업무
정보를 찾아 정리하는 기능입니다.

이 PDF들은 스캔 이미지가 아니라 문서 안에 글자와 표 정보가 이미 들어 있는 형식입니다.
그래서 사진 속 글자를 새로 읽는 일반 OCR보다는, PDF 안의 글자와 표 구조를 이용해
정해진 항목을 찾는 **현재 양식 전용 정보 추출 기능**에 가깝습니다.

개발용 60건에서는 800개 항목 모두, 최종 확인용 20건에서는 268개 항목 모두가 내부
비교 기준과 일치했습니다. 다만 이 결과는 현재 r1과 같은 구조의 합성 PDF에 대한
결과입니다. 스캔본·사진·손글씨·임의의 기업 문서까지 정확히 처리한다는 뜻은 아닙니다.

## 1. 어떤 문서를 처리하는가

대상은 `synthetic-customs-pdf-2000/20260811-r1`의 최종 합성 PDF 6,000개입니다.

| 문서 종류 | 이 문서가 담는 정보 | 문서 수 | 한 문서에서 찾는 항목 수 |
| --- | --- | ---: | ---: |
| B/L (선하증권) | 누가 어떤 화물을 어느 항로로 보내는지 | 2,000 | 13 |
| Invoice (상업송장) | 거래 당사자·품목·금액 | 2,000 | 15 |
| Packing List (포장명세서) | 포장·수량·중량·부피 | 2,000 | 12 |

문서마다 숫자, 문서번호, 일반 텍스트를 같은 기준으로 비교할 수 있도록 정리 규칙을
정했습니다. 수량·금액·무게는 수치로, 문서번호는 식별자로, 회사명·항만·품명은 일반
텍스트로 비교합니다. 아래에는 실제 값이 아니라 **어떤 항목을 찾는지**만 적습니다.

### B/L에서 찾는 13개 항목

| 구분 | 항목 | 쉬운 설명 |
| --- | --- | --- |
| 문서·운송 식별 | `bl_no`, `container_no`, `seal_no`, `voyage` | B/L 번호, 컨테이너 번호, 봉인 번호, 항차 |
| 당사자·항로 | `exporter_name`, `consignee`, `load_port`, `disch_port`, `final_dest` | 수출자, 수하인, 선적항, 양륙항, 최종 목적지 |
| 화물·운송 | `vessel`, `good`, `gross_weight`, `containers` | 선박, 품명, 총중량, 컨테이너 수 |

### Invoice에서 찾는 15개 항목

| 구분 | 항목 | 쉬운 설명 |
| --- | --- | --- |
| 거래 당사자·운송 | `exporter_name`, `importer_name`, `consignee`, `load_port`, `disch_port`, `vessel` | 수출자, 수입자, 수하인, 선적항, 양륙항, 선박 |
| 문서 식별 | `inv_no`, `inv_date`, `lc_no` | 인보이스 번호, 인보이스 일자, 신용장 번호 |
| 품목·금액 | `good`, `qty`, `unit`, `unit_price`, `amount`, `total` | 품명, 수량, 단위, 단가, 품목 금액, 합계 금액 |

### Packing List에서 찾는 12개 항목

| 구분 | 항목 | 쉬운 설명 |
| --- | --- | --- |
| 당사자·문서 식별 | `exporter_name`, `consignee`, `inv_no`, `lc_no` | 수출자, 수하인, 인보이스 번호, 신용장 번호 |
| 포장·품목 | `good`, `qty`, `unit`, `cartons`, `cbm` | 품명, 수량, 단위, 상자 수, 부피 |
| 중량 | `net_weight`, `gross_weight`, `net_gross_weight` | 순중량, 총중량, 문서에 보이는 순·총중량 표현 |

Packing List에는 `containers`를 넣지 않았습니다. 최종 PDF에서 컨테이너 수를 뜻하는
전용 값 칸이 실제로 보이지 않았기 때문입니다. B/L의 값, CSV, 같은 묶음의 다른 문서로
빈칸을 채우지 않습니다. 확인할 수 없는 값을 그럴듯하게 추정하지 않는 것이 이 기능의
기본 원칙입니다.

`net_gross_weight`도 다른 문서에서 가져오는 값이 아닙니다. Packing List 안에 보이는
순중량과 총중량 정보를 정해진 표현으로 함께 다루는 이 문서만의 항목입니다.

## 2. 어떻게 값을 찾는가

PDF 안에 이미 들어 있는 글자와 표의 구조를 이용합니다. 문서 안의 글자 조각, 읽는 순서,
표의 칸을 살펴보고, 그중 어느 것이 “수하인”, “품명”, “수량”, “합계 금액”에 해당하는지
찾습니다.

```text
PDF 안의 글자·표 구조
        ↓
현재 양식에서 항목을 찾는 선택 규칙
        ↓
B/L·Invoice·Packing List의 정해진 항목
        ↓
사람이 확인할 수 있는 추출 후보
```

현재 방식은 PaddleOCR나 Docling 같은 신경망 OCR의 가중치를 다시 학습하거나
파인튜닝한 결과가 아닙니다. 문서별 정답 목록을 저장하는 방식도 아닙니다. r1과 같은
양식에서 항목과 값을 연결하는 방법을 학습한 작은 선택 규칙을 사용합니다.

이 때문에 같은 양식에서 값만 달라진 문서는 처리할 수 있지만, 표의 모양이나 항목 이름,
배치가 달라진 새 문서에서는 같은 결과를 약속할 수 없습니다.

## 3. 왜 처음의 일반 OCR 후보만으로는 부족했는가

처음에는 PDF의 단순 텍스트 추출, PaddleOCR, Docling, PDF 표·선 정보를 이용한 방법을
같은 개발 문서에서 비교했습니다. 이 방법들은 글자 일부나 표 일부를 읽을 수는
있었습니다. 하지만 “이 숫자가 수량인지 금액인지”, “이 회사명이 수출자인지
수하인인지”처럼 **항목과 값의 관계**를 안정적으로 찾지는 못했습니다.

| 비교한 방법 | 항목 정확도 | 문자 오류율 | 표 정합도 | 결과 |
| --- | ---: | ---: | ---: | --- |
| Docling Fast | 244 / 800 (0.305) | 0.297586 | 0.566990 | 기준 미달 |
| PaddleOCR 3.2 | 156 / 800 (0.195) | 0.407480 | 0.000000 | 기준 미달 |
| PDF 표·선 정보 기반 v10 | 360 / 800 (0.450) | 기준 통과 | 기준 통과 | 항목 정확도 미달 |

이 실패는 데이터가 섞였거나 깨졌다는 뜻이 아닙니다. 평가 전에는 대상 PDF, 문서 식별값,
PDF 지문(SHA), 비교할 항목 수가 모두 맞는지 확인했습니다. 글자를 읽는 능력과 업무상
항목을 정확히 연결하는 능력은 서로 다른 문제였던 것입니다.

통과하려면 아래 세 기준을 모두 만족해야 합니다.

- **항목 정확도(Field exact)**: 0.99 이상
- **문자 오류율(CER)**: 0.01 이하
- **표 정합도(Table F1)**: 0.98 이상

셋 중 하나라도 기준에 못 미치면 다음 단계인 최종 확인 평가와 자동 활성화를 하지
않습니다.

## 4. 학습과 평가는 어떻게 나누었는가

같은 세트에서 나온 정상·오류 버전(clean/error)이나 B/L·Invoice·Packing List가
학습과 평가에 나뉘어 들어가면, 답을 외우지 않았더라도 너무 비슷한 문서를 본 셈이
됩니다. 그래서 같은 세트 번호에서 나온 관련 문서를 하나의 묶음(family)으로 보고
함께 나눴습니다.

| 구분 | 수량 | 의미 |
| --- | ---: | --- |
| 개발 평가 | 60 PDF / 800개 항목 | 방법을 확인하고 개선하는 문서 |
| 최종 확인 평가(봉인 평가) | 20 PDF / 268개 항목 | 방법과 계약을 고정한 뒤 한 번만 실행하는 문서 |
| 평가에 사용된 관련 문서 묶음 | 78 | 개발·최종 확인 PDF가 속한 세트 번호(set-number) 기준 묶음 |
| 학습에서 제외한 PDF | 468 | 위 78개 묶음의 정상·오류 버전과 세 문서 종류 전체 |
| 학습에 사용한 PDF | 5,532 | 문서 종류 3개 × 정상/오류 2개의 6개 구분(strata)마다 922개 |
| 자동으로 만든 학습 항목 라벨 | 73,760 | B/L 23,972, Invoice 27,660, Packing List 22,128 |

학습 라벨의 기준값은 최종 PDF에 실제로 보이는 내용을 바탕으로 만듭니다. 하지만 각
항목 라벨에는 항목 이름, 비교 규칙, 정리된 값의 SHA-256만 남깁니다. 실제 값, 원래
분석기의 고정 run 번호·고정 위치·원본 템플릿 profile은 라벨과 모델에 넣지 않습니다.

라벨 영수증에는 문서 ID, PDF/source SHA, 문서 종류, family 번호처럼 “이 문서가 학습에
써도 되는 문서인지”를 확인하기 위한 정보가 남습니다. 이 정보는 파일이 바뀌지 않았는지
확인하는 데만 쓰며, 모델이 어떤 항목 값을 고를지 결정하는 입력은 아닙니다. 모델 자체에는
문서 ID, source SHA, 실제 값, label hash가 없습니다.

모델에는 후보 PDF에서 배운 위치·읽기 순서·표 구조 선택 규칙이 있을 수 있습니다. 이는
현재 양식에서 항목을 찾기 위한 규칙이며, source compiler의 고정 위치를 실행 중에 가져와
쓰는 방식은 아닙니다.

## 5. 실제 평가는 어떻게 했는가

비교 기준도 CSV에서 가져오지 않았습니다. 최종 PDF에 실제로 표시된 내용을 읽어 자동으로
만든 내부 대조값을 사용했습니다. 대상 PDF와 비교 기준은 각각의 SHA와 평가 묶음으로
연결되어 있어, 다른 PDF나 다른 비교 기준을 섞으면 점수를 내기 전에 중단합니다.

개발 평가와 최종 확인 평가는 서로 다른 관련 문서 묶음이며 같은 세트 번호도 겹치지
않습니다. 다만 두 평가의 내부 대조값은 모두 같은 최종 PDF 해석 방식으로 만들어졌습니다.
따라서 문서가 섞이는 문제는 막았지만, 사람이 따로 만든 정답지나 실제 업무 원본으로
검증한 일반 OCR 평가는 아닙니다. 이 평가는 r1 템플릿이 일관되게 처리되는지를 확인하는
검증입니다.

| 평가 단계 | 문서 구성 | 비교한 항목 수 | 항목 정확도 | 문자 오류율 | 표 정합도 | 결과 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 개발 | B/L 20, Invoice 20, Packing List 20 | 800 | 800 / 800 | 0.0 | 1.0 | 통과 |
| 최종 확인 | B/L 7, Invoice 7, Packing List 6 | 268 | 268 / 268 | 0.0 | 1.0 | 통과 |

점수는 다음을 뜻합니다.

- **항목 정확도**: 문서마다 정한 비교 규칙으로 값을 정리한 뒤, 내부 대조값과 정확히
  맞은 비율입니다.
- **문자 오류율**: 추출한 텍스트에서 내부 대조값과 다른 문자의 비율입니다. `0.0`은
  이번 평가 대상에서 문자 차이가 없었다는 뜻입니다.
- **표 정합도**: 표의 칸 위치와 내용이 내부 대조값과 얼마나 맞는지 나타냅니다. `1.0`은
  이번 평가 대상의 모든 비교 칸이 맞았다는 뜻입니다.

최종 확인 평가는 개발 결과를 본 뒤 반복해서 고칠 수 있는 단계가 아닙니다. 최종 확인용
후보 실행과 평가 기록은 한 번만 만들 수 있게 하고, 선택 결과·평가 문서·모델·설정이
서로 맞을 때만 통과시킵니다.

## 6. 통과한 뒤에도 왜 다시 확인하는가

점수가 통과했다고 해서 한 번 올린 기능을 계속 믿지 않습니다. PDF 요청을 처리할 때마다
다음 정보가 서로 맞는지 다시 확인합니다.

- 어떤 r1 데이터셋과 개발·최종 확인 문서로 평가했는지
- 현재 허용된 r1 추출기인지
- 모델 파일, 학습 기록, 학습 분리 기록, 라벨 기록이 바뀌지 않았는지
- 개발 선택, 최종 확인 실행, 최종 확인 평가 기록이 모두 한 체인인지
- 파일 지문(SHA-256), JSON 형식, 파일 누락·변조 여부가 올바른지

하나라도 맞지 않으면 이전 엔진으로 조용히 바꾸지 않습니다. 대신 사용 불가
(`unavailable`)로 끝냅니다. 잘못된 결과를 그럴듯하게 보여 주는 것보다, 결과를 내지
않는 쪽이 안전하기 때문입니다.

또한 이 기능은 PDF 미리보기와 항목 후보를 만드는 기능입니다. 자동 Finding, 통관 판단,
자동 검토 입력을 만들지 않습니다. 사람이 확인하고 수정한 뒤 텍스트로 확정된 정보만
기존 심사 흐름에 전달됩니다.

## 7. 이 결과를 어떻게 이해해야 하는가

| 지금 확인된 것 | 아직 확인되지 않은 것 |
| --- | --- |
| 현재 r1과 같은 형식의 합성 PDF에서 필요한 항목을 안정적으로 찾을 수 있다. | 스캔 PDF, 사진, JPEG/PNG, 손글씨, 흐린 문서, 도장 겹침 |
| 같은 세트의 형제가 학습과 평가에 섞이지 않도록 문서 묶음을 분리했다. | 실제 기업 문서나 새로운 양식의 통관 서류 |
| 개발과 최종 확인 평가가 모두 통과했다. | 사람이 만든 독립 정답 또는 외부 업무 원본으로 확인한 일반화 성능 |
| 파일·모델·평가 기록이 바뀌면 결과를 내지 않도록 막았다. | 처음 보는 양식에서 항목 의미를 스스로 이해하는 능력 |

새 양식이나 실제 기업 문서까지 지원하려면 그 범위를 위한 별도 데이터와 독립 정답,
새로운 개발·최종 확인 평가가 필요합니다. 지금의 1.0 점수를 그 범위까지 확대 해석하거나,
기준을 낮춰 활성화하는 것은 허용하지 않습니다.

## 8. 기술 상세와 관련 문서

위 설명을 구현과 정확히 연결하기 위한 식별값은 아래와 같습니다.

| 항목 | 값 |
| --- | --- |
| 평가 범위 | `synthetic_r1_supervised_native_template_compatibility` |
| 추출 엔진 | `pdf_text_layer` |
| extractor revision | `pypdf-5.3.1-supervised-template-r1-v1` |
| candidate parser | `synthetic-pdf-supervised-template-normalizer-v11` |
| 모델 종류 | `native_pdf_semantic_model` |
